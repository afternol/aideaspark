## アイデア生成パイプライン強化（2026-04-28）

### 背景
外部評価フィードバック（複数アイデアのレビュー）から、生成されたアイデアに以下の体系的問題が判明した。

### 判明した問題パターン
1. **新規性・参入障壁の過大評価**: 国産競合を見落として novelty 4〜5・moat 4〜5 を付ける。英語検索中心だと国産SaaSが見落とされやすい
2. **絶対表現の無根拠断言**: 「国内初」「空白地帯」「担任負担ゼロ」「補助金対象」等を検証なしで記述
3. **パターンタグの内容不整合**: 月額SaaS収益なのに「アウトカム課金」、国内BtoBなのに「クロスボーダーEC」、施行済み規制に「規制変化の窓」等
4. **収益単価の楽観的設定**: 競合の公開料金帯を参照せずに単価を設定
5. **法規制リスクの楽観的評価**: 「薬機法回避可能」「実現しやすい」等、規制産業での難所を過小評価
6. **スコア平均の過大**: 全体平均が4超になるケースが多く、現実から乖離

### 実施した改善（ai-generate/route.ts）

#### Phase 1の強化
- 市場動向調査に加え、**国産競合の日本語検索**を必須化
- 「{テーマ} サービス 日本 スタートアップ」「{テーマ} SaaS 国産 2024 2025」を検索してPhase 2の入力に渡す

#### Phase 2 システムプロンプトの強化
- **スコアリングの厳格基準を明示**: 国産競合3社以上存在→novelty最大3点、公的データ中心→moat最大3点、規制産業リスク未解消→feasibility最大3点
- **絶対禁止表現リストを追加**: 「国内初」「業界初」「担任負担ゼロ」「完全自動化」「補助金対象」「〇〇はほぼ存在しない」等
- **パターンタグ整合性ルールを追加**: 収益構造・価値提供の核心と一致するパターンのみ選択可
- **収益単価の現実的設定指示**: 競合料金帯参照・B2C月額3,000〜5,000円バンド・B2G購買プロセスの考慮
- **スコア平均の上限規定**: 全6スコア平均4.0超を禁止

#### Phase 2 フィールドガイドの強化
- competitors: Phase 1で調査した国産競合を必ず含める
- scoreComments.novelty: 既存国産サービス名を1〜2社挙げて差別化軸を述べる
- noveltyNote: 「存在しない」「空白地帯」禁止。最も近い国産競合を名指しした対比構造に変更
- patternRationale: パターンIDとアイデアの収益・価値提供の対応を具体的に記述

#### Phase 3 ファクトチェックの強化（5グループ13ルールに拡張）
- **国産競合の追加調査**（旧6ルール→新13ルールに拡張）
- **noveltyスコア検証**: 類似国産サービス3社以上→novelty3以下に修正
- **moatスコア検証**: 公的データ中心→moat3以下に修正
- **feasibilityスコア検証**: 規制産業リスク未解消→feasibility3以下
- **スコア平均の確認**: 平均4.0超なら最も楽観的項目を1点引き下げ
- **パターン整合性確認**: 不整合パターンを削除して適切なIDに差し替え
- **補助金断言の検証**: 要件未確認なら「可能性がある」に修正

### 期待される改善効果
- novelty・moat の楽観的付与が構造的に抑制される
- 「国内初」「空白地帯」等の無根拠断言が自動修正される
- パターンタグの内容整合性が向上する
- 競合調査が英語圏バイアスなく国産SaaSを捕捉する

## strengthNote専用ファクトチェック（全200件）（2026-04-28）

### 実施概要
- 対象: Supabase Ideaテーブル #1〜#200（全200件）
- チェックフィールド: **strengthNote**（「何が良いのか」）専用
- 手法: 10グループ×20件・10並列エージェント × WebSearch
- 修正件数: **strengthNote直接修正0件 / 隣接フィールド4件修正**

### 主な知見

#### strengthNoteの特性
- 全200件のstrengthNoteは「データフライホイール」「スイッチングコスト」「ネットワーク効果」「先行者優位」「Unit Economics優位性」等の**抽象的優位性記述**が中心
- 抽象的優位性の主張は「ファクトチェック可能な具体的事実」を含まないため、誤り率がほぼゼロ
- 他フィールド（competitors・noveltyNote等）のような「固有名詞・数値・法令名」が少ないため、事実誤認が生じにくい構造

#### 隣接フィールド4件修正（strengthNote検証中に発見）
- 誤記はstrengthNoteではなく、検証過程で参照したcompetitors・noveltyNote等に発見
- 4件はSupabase UPDATEで修正済み

### 監査設計上の教訓
- **strengthNoteは今後のファクトチェックの優先度を下げてよい**（抽象記述なので誤り率が構造的に低い）
- 限られた監査リソースはwhyNow・noveltyNote・competitors・scoreCommentsに集中すべき
- 「何が良いのか」という問いに対する回答は、根拠となる市場データ・法令・競合動向が間接的にしか関わらないため、他フィールドで事実を担保すれば品質は自動的に担保される

### 新発見パターン

#### ω. 廃止サービスがnoveltyNote内に競合として残存（G1発見）
- ペットみるん（東京電力EP）: 2020年5月31日サービス終了済みなのに競合として記載
- ORBISのcocktail graphy: 2023年9月終了済みなのに「存在しない」の根拠として使えない
- **対策**: noveltyNoteの「〇〇は存在しない」「〇〇市場は空白」という記述を検証する際、その根拠として使っているサービスも存在確認必須

#### α'. 数値の「倍率」と「増加率」の混同（G6発見）
- 「前年度比131%増」と「前年度比131%（=1.31倍）」は全く異なる
- 国税庁発表の「対前年比131.4%」は「1.314倍」の意味（増加率は31.4%）
- **対策**: 「前年度比△△%増」と「前年度比△△%」は区別して記述。出典の原文表現を確認する

#### β'. 市場予測値の時点・出所の誤記（G7発見）
- 睡眠市場「2030年2,162億円」の出所が不明で、実際の矢野経済研究所予測は「2027年160億円」
- 現在値と将来予測値、国内と国外の数値を混在させるパターンが多い
- **対策**: 市場規模数値は「〇〇年・〇〇調査・国内/世界」の3軸を必ず明記する

#### γ'. 法令の根拠条文・命令名の誤記（G8発見）
- 人的資本開示義務の根拠: 「金融商品取引法」ではなく「企業内容等の開示に関する内閣府令」
- 法律の改正と省令・内閣府令の改正を混同するパターン
- **対策**: 法令記述は「法律名」「省令/政令/内閣府令名」「施行日」の3点セットで確認

### 新発見パターン

#### τ. 国家・政府機関の無償OSSリリースによる競合強度急上昇（G1発見）

#### υ. 金利・マクロ経済環境変化による市場背景の更新（G2発見）

- 産学連携「急増・大幅拡充」→ 根拠となる統計未確認
- 「CtoCの農機貸借手段がほぼない」→ AGRICOM（2020年〜）が存在した
- **対策**: 「急増」「唯一」「ほぼない」は必ずファクトベースで根拠を要求

### 監査の教訓・改善提言

1. **アイデア生成時にWebSearch必須化**: 生成段階でリアルタイム検索を組み込めば初期品質が大幅向上
2. **competitors は生成後即時確認**: 「廃止済みサービスを競合に書く」は最多ミス。サービス稼働確認APIや定期バッチが有効
3. **数値には必ず出典注記を**: 生成AIは出典なしに数値を混入させやすい。「数値を書くなら出典を書く」をルール化
4. **法規制フィールドは更新トリガーを設ける**: 義務化・施行日・適用範囲は変わる。法改正ニュースをトリガーに自動フラグ立てを検討
5. **competitors フィールドは6ヶ月ごとに再生成推奨**: 競合状況は最も陳腐化が早い。定期自動更新の仕組みが必要
6. **「義務化」「唯一」「急増」はハルシネーションのシグナル**: これらのキーワードが含まれるフィールドを優先的にファクトチェック
7. **EU規制は一次テキスト確認を徹底**: 改正が重なる規制は法律事務所の最新解説を一次ソースとして扱う

## エクスポート

### html2canvasはTailwind v4のoklch/lab色を解析できない（2026-04-04）
- **状況**: カスタマイズ版のPDFエクスポートで `html2canvas` が `Attempting to parse an unsupported color function "lab"` エラー
- **原因**: Tailwind v4は内部で `oklch()` / `lab()` 色関数を使用。html2canvas 1.4.1はこれらに非対応。ページ内のDOM要素をキャプチャする際、親要素から継承されるTailwindのCSS変数が解析に失敗する
- **解決**: `iframe` を使って完全に隔離した環境を作成。iframe内にTailwind CSSが一切漏れない純粋なHTMLドキュメント（hex色のみ）を書き込み、その `body` をhtml2canvasでキャプチャ
- **教訓**: html2canvasを使う場合、親ページのCSSフレームワークの色形式に注意。最新CSSカラー関数（oklch, lab, lch等）は非対応。iframe隔離が安全策

### PDFのページ境界で文字が切れる問題（2026-04-04）
- **状況**: jsPDFで複数ページのPDFを生成すると、297mm間隔の機械的スライスでテキストの途中で切断される
- **解決**: キャンバスのピクセル行をスキャンし、改ページ候補位置の前後±40mm範囲で「最も白い行」（セクション間の空白）を探してそこで分割。各スライスを個別キャンバスに切り出してPDFに配置。2ページ目以降は上部に8mmマージン追加
- **教訓**: html2canvas + jsPDFの複数ページ出力では、単純な固定高さスライスは使えない。空白行検出アルゴリズムを入れることでテキスト切れを防止できる

### Word出力にはdocxライブラリが最適（2026-04-04）
- **状況**: クライアントサイドでWord文書を生成する必要があった
- **選定**: `docx` ライブラリ + `file-saver`。テキストとしてコピー・編集可能なネイティブ.docxを生成
- **注意点**: `file-saver` には `@types/file-saver` の型定義が別途必要（ないとNext.jsのビルドでType error）
- **教訓**: PDF（画像ベース）とWord（テキストベース）は別々の生成ロジックが必要。Wordはdocxライブラリで構造化ドキュメントを直接組み立てるのが最もクリーン

## UI/UX

### ツールチップの z-index 問題（2026-04-02）
- **状況**: トレンドヒートマップのタイルにホバーで表示されるツールチップが、隣接タイルに隠れて読めない
- **原因**: `flex-wrap` で複数行になるタイル群で、後の行のタイルが前の行より z-index が高くなるため、上に表示するツールチップが被る
- **解決**: タイル自体に `hover:z-50`、ツールチップに `z-[100]` を付与。Tailwind の `group/name` でネスト対応
- **教訓**: `position: relative` な要素が並ぶ場合、ツールチップは要素単体の z-index だけでなく、hover 時に親のスタッキングコンテキストを引き上げる必要がある

### ブックマーク（localStorage）vs コレクション（DB）の二重管理（2026-04-02）
- **状況**: カード上の保存ボタンが `useBookmarkStore`（localStorage）で、コレクション機能は API 経由で DB に保存。2つが別系統で同期しない
- **解決**: 全画面の保存ボタンを `AddToCollection` コンポーネントに統一。compact プロップでアイコンのみ表示に対応
- **教訓**: 「とりあえず localStorage で」の仮実装は、後から DB 版との統一コストが全コンポーネントに波及する。保存系機能は最初から永続化先を統一すべき

### エンゲージメントボタンはカード一覧にも出す（2026-04-02）
- **状況**: リアクション（いいね・気になる・参考になった）が詳細ページにしかなく、一覧から押せない
- **解決**: `IdeaSummaryCard` にリアクションボタンを埋め込み、API に種類別カウント + ユーザーリアクション状態を返す拡張を実施
- **教訓**: エンゲージメント導線は「見る場所 = 押せる場所」にする。一覧カードにアクションがないと詳細を開く動機が薄い

### 不要な情報の削除判断（2026-04-02）
- **状況**: アイデア詳細のタグ行に「難易度: 低/中/高」バッジがあったが、フィルター検索には使われておらず、6軸スコアで実質カバーされていた
- **解決**: 指摘を受けて即削除
- **教訓**: 表示項目は「ユーザーがその場で意思決定に使うか」で判断。飾りの情報はノイズになる

### 汎用AIとの差別化を常に問う（2026-04-02）
- **状況**: AIアイデア壁打ち機能を検討した際、「ChatGPTと何が違うのか」と指摘を受けた

### 再カスタマイズは選択中バージョンをベースにする（2026-04-04）
- **状況**: マイアイデアの「再カスタマイズ」ボタンが元アイデア詳細ページへのリンクだった。複数バージョンがあっても常にオリジナルからやり直しになる

- **教訓**: 機能は「今のユーザー数・利用頻度で意味があるか」で判断。将来のための先行実装は負債になる
